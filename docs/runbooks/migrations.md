# Migrations

1. Add `packages/server/src/db/migrations/NNNN_<feature>_<what>.sql` (one tx per file; expand/contract; renames via views). Never rewrite an already-committed file. For a new CHECK, prefer `NOT VALID` then a follow-up `VALIDATE CONSTRAINT` in the next file. Mark an N-1-safe extra with the exact line `-- foundation-n1-compatible` so `migrateUp` records it in `schema_n1_compat`.
2. Locally: `pnpm db:up && DATABASE_URL=postgres://postgres:postgres@localhost:55432/foundation_dev pnpm migrate --up`, then `pnpm migrate --check schema.sql --write` and review the diff of `schema.sql`.
3. CI runs `pnpm test:pg` (migrations from empty on postgres:16).
4. Release: run `migrate --up` as the migrator role BEFORE starting the new image (release command / pre-deploy step). The app boots on `match`, or on `ahead` when extras are a unique contiguous chain declared in `schema_n1_compat`. Pending known files, checksum mismatches, skipped/duplicate ordinals, and undeclared extras refuse (`/health/ready` → 503, boot throws). Isolated restore requires `match`. `migrate --status` prints `state`.
5. `--repair`: only after a reviewed, no-op edit to an already-applied file (comment fix). Re-records checksums. Never use it to hide a real drift; write a new migration instead.
6. Rollback: N-1 means roll the **image** back and keep the new schema. The previous image must boot (`state=ahead`) because the extra file declared N-1. Do not run `migrate --up` from the old image — it still refuses applied files that are missing on disk. Write a follow-up contract migration if the rolled-back image cannot live with the new columns/constraints.
